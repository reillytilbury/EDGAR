# EDGAR Global Codebase Summary (`code_summary.md`)

## Project Overview

EDGAR (Equation Discovery with Generative AI and Reinforcement learning) is an advanced AI system designed for the automated discovery of scientific equations and models. It employs an evolutionary algorithm (EA) to iteratively evolve program-based solutions to scientific problems. Large Language Models (LLMs) are integrated into this loop to propose new program variations, leveraging insights from the performance and structure of existing programs. The system is highly adaptable, allowing for problem-dependent scoring metrics (e.g., mean-squared error against experimental data) and diverse model representations (simple equations, neural networks, etc.). The overarching goal is to discover programs that achieve optimal scores for a given scientific task.

## Repository Structure and Core Functionality

The `edgar/` directory is organized into several key modules, each addressing a specific aspect of the AI-driven scientific discovery pipeline.

### `edgar/__init__.py`
An empty package initializer, marking `edgar` as a Python package.

### `edgar/cli.py`
The Command Line Interface (CLI) serves as the primary entry point for managing EDGAR projects and executing experiments. It provides the following functionalities:
-   **`init-project <task_name>`**: Scaffolds a new project directory under `projects/` (or `experiments/` if that exists). It creates essential configuration files (`config.yaml`), placeholder seed programs (`modelX.py`, `param_estX.py`), and data/feedback handlers (`load_data.py`, `plot.py`). This establishes a ready-to-fill structure for new scientific tasks. Existing files are overwritten.
    -   Templates like `SPEC_TEMPLATE_DATA_LOADER` define expected signatures for project functions, including `load_data` (returning `(X_discover, X_validate, X_eval)` with specific data splits) and `loss_fn` (computing per-sample losses).
    -   `SPEC_TEMPLATE_MODEL` defines a `model` function accepting `data` and `params`, returning `np.ndarray` predictions, and includes a `DEFAULT_PARAMS` attribute.
    -   `SPEC_TEMPLATE_PARAM_EST` defines a `parameter_estimator` function returning a dictionary of estimated parameters.
    -   `SPEC_TEMPLATE_PLOT` defines `plot_model_fits` for visualizations.
-   **`validate <task_name>`**: Checks a project's readiness by verifying the existence of required files (e.g., `model1.py`, `load_data.py`, `config.yaml`) and the presence of expected functions (`model`, `parameter_estimator`, `load_data`, `loss_fn`, `plot_model_fits`) within them, ensuring a correct setup before execution.
-   **`run <config_path>`**: Initiates an EDGAR experiment from a `config.yaml` or a previously saved `task_spec.yaml`. It supports command-line overrides for configuration parameters (`--section.key=value`, e.g., `--evolution.n_generations=20`), with values parsed as Python literals where possible. It also allows setting various logging verbosity levels (`compact`, `code`, `prompts`).
-   **`test <config_path>`**: Executes a scaled-down test experiment with real LLM calls, useful for rapid iteration and validation. This command applies a set of predefined `TEST_OVERRIDES` (e.g., `--evolution.n_generations=1`, `--scoring.gradient_descent.max_iter=100`) to reduce the computational burden.
-   **`test-fake`**: Runs an end-to-end pipeline using mocked LLM responses, enabling testing without requiring LLM API access by utilizing the `tests.system.fake_runner`.
-   **`dashboard [<run_dir>]`**: Launches a web-based dashboard for real-time monitoring and post-hoc analysis of EDGAR runs. It can target a specific run directory (containing `task_spec.yaml`), a `program_databases/` root, or scan the default location (`./program_databases`). It allows specifying `port` and `host`, and a `--no-open` flag to prevent automatic browser launch. The `_find_free_port` helper ensures a dynamic port assignment to avoid conflicts.

### `edgar/dashboard/`
This module provides a self-contained FastAPI web server for visualizing and inspecting EDGAR runs. It offers both live monitoring of ongoing experiments and detailed post-hoc analysis, interacting with run artifacts solely via disk reads (no shared-memory IPC).
-   **`__init__.py`**: Exports key data loading functions from `data.py` for direct access within the package, including `list_runs`, `load_run_summary`, `load_live_state`, `load_program_list`, and `load_program_detail`.
-   **`data.py`**: Handles the loading and serialization of run artifacts (e.g., population history, island census, task specifications, run status) into JSON-safe Data Transfer Objects (DTOs) for the frontend. It includes caching mechanisms (`_POP_CACHE`, `_CENSUS_CACHE`) for performance, keyed by file path and modification time, ensuring efficient updates during live runs. It defines `_clean` for recursively converting numpy types and `NaN`/`inf` to JSON-compatible values. Functions for run discovery (`list_runs`), generating summary cards (`_run_card` with `started_at_ts`, `n_programs`, `best_loss`), and fetching detailed program information (`load_program_list`, `load_program_detail`) are provided. It defines `STALE_THRESHOLD_S` and `_derived_state` to identify runs that ceased updating without a `failed` status. `load_run_summary` includes `git_sha`, `git_dirty`, `created_at`, `n_alive`, `n_scored_discover`, and LLM/prompt configuration details. `load_live_state` calculates `eta_s` and includes `_islands_payload`, `_best_per_gen`, `_best_program`, and `_success_rates_latest_gen` for real-time metrics. `load_program_detail` now includes `children`, `sample_losses_summary`, `fingerprint_shape`, and dedicated `_image_url_for` and `_fit_image_url_for` helpers. The `_llm_name` helper also handles `CyclingModel` objects (from fake LLM runs) and lists of strings. `load_program_list` uses a `_sort_key` to order programs by rank, then loss, then index.
-   **`latex_cache.py`**: Implements on-demand LaTeX equation rendering for evolved programs. It leverages an LLM (the `jax_model_translator_llm` specified in the run's `task_spec.yaml`) to parse the `model` source code and generate its mathematical representation in LaTeX, using a prompt defined in `_LATEX_PROMPT`. Results are aggressively cached on disk (`<run_dir>/latex_cache/{idx}.json`) to ensure fast, free retrieval for subsequent requests. It includes robust error handling for LLM API calls, raising `RuntimeError` for failures like missing API keys or quota issues.
-   **`server.py`**: The core FastAPI application that exposes API endpoints for the dashboard. It uses `build_app` to configure roots for run discovery and optionally a default run. It serves a static Single Page Application (SPA) frontend and handles requests for run summaries, live state, program details, LaTeX equations (via POST for generation), and generated feedback/fit images. It resolves `run_id` to on-disk directories from configured `run_roots` using `_resolve`.
-   **`static/`**: Contains the HTML, JavaScript (Alpine.js-driven `app.js` for UI logic, Plotly.js for charting, KaTeX for LaTeX rendering, Highlight.js for code syntax highlighting, Marked for Markdown parsing), and CSS assets for the interactive frontend.

### `edgar/evolution/`
This module encapsulates the core logic of the evolutionary algorithm, managing the programs and their dynamics across "islands."
-   **`__init__.py`**: An empty package initializer.
-   **`program.py`**: Defines the `Program` dataclass, the fundamental unit of evolution. Each `Program` includes:
    *   `BirthCertificate`: Metadata about its origin (generation, island, batch index, parentage, mode, temperature, LLM name).
    *   `Code`: Stores the Python source code for the numpy `model`, the `parameter_estimator`, and the JAX-translated model (`model_jax`).
    *   `name`: A descriptive name provided by the LLM.
    *   `program_losses`: Stores initial and final scalar losses for `discover` and `validate` splits, including a complexity penalty. `NotValidated` is a sentinel class marking programs not yet prepared for validation scoring. `LossPair` and `Losses` dataclasses structure these.
    *   `sample_losses`, `sample_losses_init`: Per-sample loss values (no penalty) for final and initial parameters respectively, used for analysis.
    *   `n_params`: The count of free parameters in the model.
    *   `eval_fingerprint`: A low-dimensional representation of model outputs used for deduplication.
    *   `params`, `params_init`: The optimized and initial parameter sets, respectively (as JAX pytrees).
    *   `image_path`, `fit_image_path`: Paths to associated visualization images.
    *   `idx`: A global unique identifier within the `Population`, set automatically upon addition.
    *   `rank`: Its final rank based on validation loss.
    *   `_default_params`: Internal storage for default parameters, with a setter that automatically calculates and caches `n_params` and handles errors gracefully, warning instead of failing.
    *   `compile_model`, `compile_param_est`: Methods to dynamically load the JAX model and parameter estimator callables from their source strings, raising `ModelLoadingError` or `ParamEstLoadingError` on failure.
    *   Properties (`descriptive_name`, `loss_discover`, `model_code`, `param_est_code`, `default_params`) provide a standardized interface for prompt templating.
-   **`population.py`**: Manages the collection of all `Program` instances throughout an experiment. It is an append-only list, automatically assigning a stable global index (`program.idx`) upon addition. This class handles the persistence of all program data (including numpy arrays for fingerprints and parameters, converted via `_params_to_json` and `_params_from_json`) to a JSONL file (`population.jsonl`) via atomic writes, ensuring data integrity during live runs. It also provides methods for `prepare_validation_scoring` (setting a program's validation loss to `None` for scoring eligibility) and retrieving a rank-sorted copy (`get_sorted`).
-   **`island.py`**: Implements the "island" model of evolutionary computation, where `n_islands` distinct populations evolve somewhat independently but exchange programs.
    *   `seed`: Initializes the `Population` with user-provided seed programs and distributes their indices across all islands.
    *   `spawn`: Selects parents (using `uniform_sample` or `boltzmann_sample`), creates new `Program` shells with `BirthCertificate` metadata, and adds them to their respective islands. `boltzmann_sample` uses a Boltzmann distribution over relative, std-normalized losses to bias selection towards better-performing programs, with a `temperature` parameter controlling the selection pressure.
    *   `prune`: Reduces the size of each island to maintain genetic diversity and computational efficiency by retaining a fixed number of the best programs, specifically `critical_population_size - n_migrants`, explicitly handling `None`/`inf` losses.
    *   `uniform_sample`: Selects `k` program indices uniformly at random.
    *   `boltzmann_sample`: Selects `k` program indices using a Boltzmann distribution over relative, std-normalized losses. It handles `NaN`/`inf` losses by converting them to `float("inf")` and then to `worst_finite + 1.0` before computing probabilities, ensuring robust sampling.
    *   `migrate`: Facilitates genetic exchange between islands. Programs are sampled via a Boltzmann distribution (with a warped temperature `T_warped = (T - 1.0) ** 4` for stronger selection later in the run) and moved to destination islands as defined by a `topology` configuration.
    *   `_are_duplicates`: Helper function to determine if two programs are functionally identical based on parameter count, loss similarity (within `loss_tol`), and high cosine similarity of `eval_fingerprint` arrays.
    *   `deduplicate_inner`: Removes functionally identical programs within an island, keeping the lower-loss version.
    *   `deduplicate_outer`: Identifies and removes duplicate programs across different islands, prioritizing the lower-loss (or lower-indexed island's) version. It assumes `deduplicate_inner` has already been run and only applies if islands exceed `min_island_size`.
    *   `deduplicate`: Orchestrates both inner and outer deduplication, using configurable `loss_tol`, `cosine_tol`, and `min_island_size` (derived from `0.75 * critical_population_size`).
    *   `save_island_census`, `load_island_census`: Manages the persistence of island membership history (generation snapshots `census[generation][island_idx] -> list[int]`) to `island_census.jsonl` using atomic writes.

### `edgar/io/`
This module handles all input/output operations, configuration, and run state management.
-   **`__init__.py`**: An empty package initializer.
-   **`config.py`**: Defines the Pydantic data models for all configuration parameters, ensuring strong typing and validation. It introduces `_LaxModel` which warns about unexpected configuration fields instead of raising errors. It includes models for `RunConfig`, `IOConfig`, `EvolutionConfig` (with validation for `topology` length and indices), `RetryConfig`, `LLMsConfig` (including supported `ValidLLMs` literal types for Gemini and Anthropic models), `GradientDescentConfig`, `ScoringConfig`, and `PromptsConfig`. The main `Config` class loads settings from `config.yaml` (merging with defaults from `projects/config_default.yaml` and project-specific `prompts.yaml` overrides) or extracts them from a saved `task_spec.yaml`.
-   **`logging.py`**: Provides structured logging for EDGAR runs, writing human-readable summaries to `run.log`. It supports different verbosity levels (`compact`, `code`, `prompts`), allowing users to control the detail captured per generation (success rates, island state, generated code, reconstructed prompts). It incorporates a `warnings.showwarning` hook (managed by `open_log` and `close_log`) to buffer and include runtime warnings in the generation log, ensuring warnings are contextualized. The `RunLog` dataclass stores log state, and `print_and_log` ensures messages are both printed to console and written to file.
-   **`plotting.py`**: Contains utilities for generating visualization images. `generate_feedback_image` creates plots for LLM image-feedback prompts (using a project-specific `plot_fn`), saving them to a structured directory (`image_feedback/gen_NNN/island_NNN/batch_NNN/image.png`) and returning image bytes. `generate_program_fits` produces comparison plots for individual programs, showing initial versus optimized model fits (`image_fits/P{idx:04d}.png`). Both rely on a project-specific `plot_fn` (defined in `image_feedback/plot.py`) which is passed as part of the `TaskSpec`.
-   **`status.py`**: Manages the atomic writing and reading of a `status.json` file, which tracks the real-time state of an EDGAR run (e.g., `starting`, `running`, `complete`, `failed`, `current_gen`, `error`, `started_at`, `updated_at`). This file is crucial for the dashboard's live monitoring capabilities. The use of `_atomic_write_json` and `atomic_write_text` ensures that external readers (like the dashboard) never encounter a partially written or corrupted status file, using a per-pid+thread temporary suffix (`.tmp.{pid}.{tid}`).
-   **`task_spec.py`**: Defines the `TaskSpec` dataclass, a frozen, comprehensive bundle of all configuration and callable functions required to execute or reproduce an EDGAR experiment.
    *   It captures `git_sha` and `git_dirty` status at creation via `_git_state` for full reproducibility. The git commands now explicitly use `REPO_ROOT` for context.
    *   It loads project-specific callables (`load_data_fn`, `loss_fn`, `plot_fn`) and seed `Program` objects directly from source code via `load_function_from_source`, facilitating dynamic code loading. It extracts `DEFAULT_PARAMS` from seed models using `_extract_default_params`.
    *   `from_config` factory method initializes the `TaskSpec` from a `Config` object, setting up the `rng` with a `random_seed` and loading seed programs.
    *   `save` method writes a read-only `task_spec.yaml` to the run directory, preserving the exact configuration and source references. Write permissions are stripped (`os.chmod(path, stat.S_IREAD)`) to prevent accidental modification.
    *   `schedule` determines the `mode` (explore/exploit), `temperature` (decaying from 2 to ~1.37 on a Gemini-scale), and specific LLM models to use for each generation, potentially cycling through lists of LLMs. It handles Anthropic-specific rescaling of temperatures in `llm_calling.py`.
    *   `output_dir` defines the hierarchical run output path (`<save_path>/YYYY-MM-DD/HH-MM-SS/`).
    *   `flat_config` provides a merged dictionary of configuration parameters for convenient lookup by prompt templating.
    *   `prompt_schemas` provides namedtuple access to `model_prompt_schema`, `param_est_prompt_schema`, and `jax_model_prompt_schema`.

### `edgar/llm/`
This module handles all interactions with Large Language Models.
-   **`__init__.py`**: An empty package initializer.
-   **`code_loading.py`**: Provides `load_function_from_source`, a utility to safely execute Python source code within a fresh namespace and return a specific named callable. This enables dynamic loading of LLM-generated code and project-specific functions, with robust error handling for `exec` failures, returning `None` on failure or if the source is invalid/empty.
-   **`generate.py`**: Orchestrates the LLM-driven generation of new `Program` components. It identifies programs needing specific code (model, parameter estimator, JAX translation) using filters like `_needs_model_code` and dispatches asynchronous calls to LLMs.
    *   `_resolve_parents`: Helper to resolve and sort parent programs by loss.
    *   `_generate_one_model`: Calls an LLM using a `ModelSchema` to generate numpy `model` code, a descriptive name, and `default_params`. It integrates with `plotting.generate_feedback_image` to provide multimodal image-based feedback to the LLM. It assigns generated default parameters to `program.default_params` using its setter, which in turn calculates `n_params`.
    *   `_generate_one_param_est`: Calls an LLM using a `ParamEstSchema` to generate numpy `parameter_estimator` code.
    *   `_translate_one_model`: Calls an LLM using a `TranslationSchema` to translate numpy `model` code into a JAX-compatible version, validating the output.
    *   `generate_models`, `generate_param_ests`, `translate_programs`: Asynchronously process batches of programs needing generation, leveraging `asyncio.gather`.
-   **`llm_calling.py`**: Provides the `call_llm` asynchronous function, a robust wrapper for interacting with various LLM providers (Google, Anthropic) via the `pydantic-ai` library.
    *   `_build_model`: Dynamically constructs PydanticAI `Model` instances based on model name prefixes (`gemini-`, `claude-`), retrieving API keys from environment variables. It raises `UserError` with clear instructions if API keys are missing.
    *   It handles `temperature` rescaling for providers with different ranges (e.g., Anthropic's [0,1] vs. Google's [0,2]) to ensure the scheduled temperature values are applied correctly, specifically mapping the Gemini-scale [1.37, 2.0] to Anthropic's [0.685, 1.0] range. It also ensures `max_tokens` is explicitly set for Anthropic models.
    *   Incorporates `RetryConfig` (passed via `config`) for handling transient HTTP errors (e.g., 500, 503) with exponential backoff and jitter. It distinguishes between retryable and non-retryable errors (e.g., `UnexpectedModelBehavior`, `UsageLimitExceeded`, `ModelHTTPError`, `ModelAPIError`, `UserError`).
    *   Supports structured output parsing using `ModelSchema`, `ParamEstSchema`, and `TranslationSchema`.
    *   Includes PydanticAI `Capabilities` (`_LogRawResponseCapability`, `_WarnOnMaxTokensCapability`) for verbose logging of raw LLM responses and warnings about response truncation or malformed function calls.
    *   Supports multimodal input by passing `image_bytes` to the LLM.
-   **`prompt_schema.py`**: Defines the `PromptSchema` Pydantic model for constructing LLM prompts. It allows for modular prompt design, separating base instructions, mode-specific instructions (explore/exploit), code guidelines, docstring guidelines, and image analysis instructions.
    *   It supports dynamic variable substitution from global configuration (`config` dict from `TaskSpec.flat_config`) and from parent/current `Program` objects (`parent_program_vars`, `current_program_vars`), enabling highly contextualized prompts that evolve with the experiment. Nested attributes in `Program` objects (e.g., `program.code.model`) are accessed via dotted paths and substituted into template variables with underscores (e.g., `{code_model}`).
-   **`response_schema.py`**: Defines Pydantic models (`ModelSchema`, `ParamEstSchema`, `TranslationSchema`) to enforce structured output from LLMs. This ensures that generated code and metadata conform to expected formats, facilitating automated parsing and integration into the EDGAR pipeline. `ModelSchema` specifically extracts the LLM's `thought_process`, a `descriptive_name`, `latex_equations`, the `code`, and `default_params` from the model generation step.

### `edgar/run.py`
This is the main orchestrator for an EDGAR experiment. The `run` asynchronous function executes the entire evolutionary loop:
-   **Initialization**: Sets JAX/XLA environment variables (`XLA_PYTHON_CLIENT_PREALLOCATE`, `XLA_PYTHON_CLIENT_ALLOCATOR`, `XLA_FLAGS`) for GPU memory management. It creates the output directory, saves the `TaskSpec`, and initializes structured logging (`run.log`) and status tracking (`status.json`). It loads data from `spec.load_data_fn` into `X_discover`, `X_validate`, `X_eval` splits. `RetryConfig` for LLM calls is also initialized.
-   **Seed Phase**: Initializes the `Population` with provided seed programs, translates their numpy models to JAX, scores them on the `discover` split, generates initial program fit visualizations (`generate_program_fits`), and saves the initial `Population` and `Island` census. The `status.json` is updated to 'running'.
-   **Generational Loop**: For each generation:
    1.  Logs generation details, including `mode` (explore/exploit), `temperature`, and the selected LLM models from `spec.schedule`.
    2.  `spawn` new programs on islands, generating empty program shells based on parent programs selected via Boltzmann or uniform sampling using `spec.rng`.
    3.  Asynchronously calls LLMs (via `edgar/llm/generate.py`) to fill in `model` code (`generate_models`), `parameter_estimator` code (`generate_param_ests`), and JAX translations (`translate_programs`) for the newly spawned programs. Image feedback for LLMs is generated here.
    4.  `score` the newly generated programs on the discover split, performing parameter estimation and gradient descent. This phase also generates program fit images.
    5.  Applies evolutionary operations: `deduplicate` programs within and across islands, `prune` islands to maintain size limits, and `migrate` programs between islands.
    6.  Logs the current generation's summary and persists the `Population` and island `census` (using atomic writes for robustness) and updates the `status.json`.
-   **Final Validation**: After the generational loop, programs are prepared for final `validate` scoring via `population.prepare_validation_scoring`, then `rank`ed based on their validation performance.
-   **Error Handling**: A `finally` block ensures that the `Population`, `census`, and `status.json` are always saved, even if an exception occurs. It captures and logs any encountered errors, marking the run status as 'failed' if an exception was raised, and includes the full traceback.

### `edgar/scoring/`
This module is responsible for evaluating the performance of generated models. It utilizes JAX for efficient numerical operations and runs scoring in subprocesses to ensure stability and enforce timeouts.
-   **`__init__.py`**: An empty package initializer.
-   **`scoring.py`**:
    *   `_get_params`: Uses the `param_est_fn` from a program to estimate initial parameters per sample. If the estimator fails or is absent, it falls back to the model's `default_params` (stacked for batch processing).
    *   `_optimize`: Performs gradient descent using `optax.adam` to fit model parameters to training data, minimizing the `loss_fn`. It tracks the best-performing parameters and loss during optimization. JAX's `vmap` and `jit` are used to parallelize and accelerate these computations across samples, and `ravel_pytree` linearizes parameters for optimization.
    *   `_eval_loss`: Computes the overall scalar loss (including a parameter complexity penalty from `param_penalty_weight`) for a model on a test dataset.
    *   `_eval_sample_losses`: Computes individual losses for each sample, without the complexity penalty.
    *   `_eval_fingerprint`: Generates a low-dimensional "fingerprint" of model outputs on a small subset of data, crucial for `deduplication`.
    *   `_worker`: A function executed in a dedicated subprocess. It deserializes a `Program` and `loss_fn` using `cloudpickle`, compiles its JAX model and parameter estimator, performs parameter estimation and optimization, calculates losses, and generates fingerprints and sample-specific losses. This isolation prevents runaway models from crashing the main process and allows for `timeout_s` enforcement.
    *   `_score_one_model`: Orchestrates the execution of `_worker` in a separate process (defaulting to "spawn" for compatibility, configurable via `EDGAR_MP_START_METHOD`). It enforces a `timeout_s`; if the subprocess exceeds the timeout, it is forcefully killed, and the program is assigned an infinite loss. It also handles cases where a program has `n_params=None` by assigning infinite loss.
    *   `_has_jax_code`, `_needs_scoring`: Filters identify programs that have ready JAX models and parameter estimators and whose specific split's `final` loss has not yet been set (or is not already `inf` or `NotValidated`).
    *   `score`: The main scoring function iterates through programs needing evaluation for a given split (`discover` or `validate`). It calls `_score_one_model` for each, then updates the program's `program_losses`, `eval_fingerprint`, `params`, `params_init`, `sample_losses`, and `sample_losses_init` fields. `X_eval` can be passed as `None` to skip fingerprint calculation (e.g., during validation).
    *   `rank`: After all validation scoring is complete, this function assigns a numerical rank to programs based on their `validate.final` loss (excluding `NotValidated` programs), providing a clear measure of final performance.

## Mathematical and Algorithmic Highlights

-   **Evolutionary Algorithm Core**: The system implements an island-model EA. Programs are represented as Python code, forming the genotype. LLMs act as mutation/crossover operators, generating new genotypes.
-   **Boltzmann Sampling**: Used for parent selection and migration, where the probability $P_i$ of selecting a program $i$ is proportional to $e^{g_i}$, with $g_i = -z_i / \max(T_{sampling}, 10^{-3})$ and $z_i = (loss_i - loss_{min}) / (std_{loss} + 10^{-6})$. This ensures that fitter programs (lower loss) have a higher chance of being selected, while the `temperature` parameter controls the exploration/exploitation trade-off. Programs with `None`, `NaN`, or `inf` losses are handled gracefully by assigning them a large finite loss value before probability calculation.
-   **Gradient Descent Optimization**: Parameters for evolved models are optimized using `optax.adam` within JAX. This allows for efficient, differentiable fitting of model predictions to data, which is critical for accurate loss calculation and performance evaluation. JAX's `vmap` and `jit` are extensively used to vectorize and compile these operations for performance, and `ravel_pytree` facilitates optimization of JAX pytrees.
-   **Deduplication Metrics**: Program similarity for deduplication is assessed via a multi-criterion approach:
    1.  Matching number of parameters (`n_params`).
    2.  Loss difference within a `loss_tol` threshold (e.g., 0.01).
    3.  Cosine similarity of `eval_fingerprint` (model outputs on a small, fixed dataset) exceeding a `cosine_tol` threshold (e.g., 0.95). This robustly identifies functionally identical or near-identical models across `deduplicate_inner` and `deduplicate_outer` operations. `min_island_size` (derived from `0.75 * critical_population_size`) dictates when cross-island deduplication is applied.
-   **Temperature Schedule**: The system dynamically adjusts the temperature for LLM generation and Boltzmann sampling. The base temperature decays from higher values (more exploration, `T=2` at generation 0) to lower values (more exploitation, `T~1.37` at `n_generations`) following `1 + exp(-generation / n_generations)`. A specific `T_warped = (T - 1.0) ** 4` transformation is applied for migration, making migration highly selective in later generations. This temperature is then rescaled for different LLM providers (e.g., Anthropic's [0,1] range) in `llm_calling.py` to match their API specifications while preserving the relative decay.
-   **JAX Integration**: Critical for performance, JAX is used for model compilation, parameter optimization, and loss calculation, enabling Just-In-Time (JIT) compilation and vectorized operations (`vmap`). This ensures that the generated models can be efficiently evaluated on large datasets and across multiple samples. JAX/XLA environment variables are set early in `run.py` to optimize GPU resource allocation.
-   **Atomic File Operations**: `edgar/io/status.py`, `edgar/evolution/population.py`, and `edgar/evolution/island.py` utilize atomic write operations (write to temp file, then rename using `_tmp_path` for concurrency safety across processes and threads) to guarantee data integrity for files that are frequently updated and polled by external processes (like the dashboard), preventing partial or corrupted data reads. `edgar/io/task_spec.py` further enforces read-only permissions on saved `task_spec.yaml` files to prevent accidental modification and preserve reproducibility.
-   **Subprocess Isolation**: Scoring of individual programs is performed in dedicated subprocesses, allowing for robust timeout enforcement and preventing unstable or resource-intensive models from crashing the main EDGAR process. This also ensures clean JAX environment initialization for each scoring task. `cloudpickle` is used for cross-process object serialization. The subprocess start method is configurable via the `EDGAR_MP_START_METHOD` environment variable (defaults to "spawn").
