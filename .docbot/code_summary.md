# EDGAR Global Codebase Summary (`code_summary.md`)

## Project Overview

EDGAR (Equation Discovery with Generative AI and Reinforcement learning) is an advanced AI system designed for the automated discovery of scientific equations and models. It employs an evolutionary algorithm (EA) to iteratively evolve program-based solutions to scientific problems. Large Language Models (LLMs) are integrated into this loop to propose new program variations, leveraging insights from the performance and structure of existing programs. The system is highly adaptable, allowing for problem-dependent scoring metrics (e.g., mean-squared error against experimental data) and diverse model representations (simple equations, neural networks, etc.). The overarching goal is to discover programs that achieve optimal scores for a given scientific task.

## Repository Structure and Core Functionality

The `edgar/` directory is organized into several key modules, each addressing a specific aspect of the AI-driven scientific discovery pipeline.

### `edgar/__init__.py`
An empty package initializer, marking `edgar` as a Python package.

### `edgar/cli.py`
The Command Line Interface (CLI) serves as the primary entry point for managing EDGAR projects and executing experiments. It provides the following functionalities:
-   **`init-project <task_name>`**: Scaffolds a new project directory under `projects/` (or `experiments/` if that exists). It creates essential configuration files (`config.yaml`), placeholder seed programs (`modelX.py`, `param_estX.py`), and data/feedback handlers (`load_data.py`, `plot.py`). This establishes a ready-to-fill structure for new scientific tasks. Existing files are overwritten.
    -   Templates like `SPEC_TEMPLATE_DATA_LOADER` define expected signatures for project functions, including `load_data` (returning `(X_discover, X_validate, X_eval)` with specific data splits) and `loss_fn` (computing per-sample losses, or `loss_fn_train`/`loss_fn_test` for separate training/testing losses).
    -   `SPEC_TEMPLATE_MODEL` defines a `model` function accepting `data` and `params`, returning `np.ndarray` predictions, and includes a `DEFAULT_PARAMS` attribute.
    -   `SPEC_TEMPLATE_PARAM_EST` defines a `parameter_estimator` function returning a dictionary of estimated parameters.
    -   `SPEC_TEMPLATE_PLOT` defines `plot_model_fits` for visualizations.
-   **`validate <task_name>`**: Checks a project's readiness by verifying the existence of required files (e.g., `model1.py`, `load_data.py`, `config.yaml`) and the presence of expected functions (`model`, `parameter_estimator`, `load_data`, `loss_fn`, `plot_model_fits`) within them, ensuring a correct setup before execution.
-   **`run <config_path>`**: Initiates an EDGAR experiment from a `config.yaml` or a previously saved `task_spec.yaml`. It supports command-line overrides for configuration parameters (`--section.key=value`, e.g., `--evolution.n_generations=20`), with values parsed as Python literals where possible. Dotted keys (`--scoring.gradient_descent.max_iter=100`) are supported for nested configuration sections. It also allows setting various logging verbosity levels (`compact`, `code`, `prompts`).
-   **`resume <run_dir>`**: Resumes a crashed or interrupted run, picking up at the next unfinished generation and writing into the same directory.
-   **`test <config_path>`**: Executes a scaled-down test experiment with real LLM calls, useful for rapid iteration and validation. This command applies a set of predefined `TEST_OVERRIDES` (e.g., `--evolution.n_generations=1`, `--scoring.gradient_descent.max_iter=100`, `--llms.num_parents=2`, `--scoring.n_param_ests=1`) to reduce the computational burden.
-   **`test-fake`**: Runs an end-to-end pipeline using mocked LLM responses, enabling testing without requiring LLM API access by utilizing the `tests.system.fake_runner`.
-   **`dashboard [<run_dir>]`**: Launches a web-based dashboard for real-time monitoring and post-hoc analysis of EDGAR runs. It can target a specific run directory (containing `task_spec.yaml`), a `program_databases/` root, or scan the default location (`./program_databases`). It allows specifying `port` and `host`, and a `--no-open` flag to prevent automatic browser launch. The `_find_free_port` helper ensures a dynamic port assignment to avoid conflicts.

### `edgar/cloud/`

The `fetch_results` command now downloads run artifacts into `program_databases/<project>/<run_name>/YYYY-MM-DD/HH-MM-SS/`, maintaining the project and timestamp hierarchy locally.

-   **`__init__.py`**: Exports key data loading functions from `data.py` for direct access within the package, including `list_runs`, `load_run_summary`, `load_live_state`, `load_program_list`, and `load_program_detail`.

It includes caching mechanisms (`_POP_CACHE`, `_CENSUS_CACHE`) for performance, keyed by file path and modification time, ensuring efficient updates during live runs. It defines `_clean` for recursively converting numpy types and `NaN`/`inf` to JSON-compatible values. Functions for run discovery (`list_runs`), generating summary cards (`_run_card` with `started_at_ts`, `n_programs`, `best_loss`), and fetching detailed program information (`load_program_list`, `load_program_detail`) are provided. The `_llm_name` helper also handles `CyclingModel` objects (from fake LLM runs) and lists of strings. `load_program_list` uses a `_sort_key` to order programs by rank, then loss, then index. `_reconstruct_model_prompt` now incorporates an "ideas-injection-point" for prompt reconstruction. -   **`latex_cache.py`**: Implements on-demand LaTeX equation rendering for evolved programs. Results are aggressively cached on disk (`<run_dir>/latex_cache/{idx}.json`) to ensure fast, free retrieval for subsequent requests. It includes robust error handling for LLM API calls, raising `RuntimeError` for failures like missing API keys or quota issues.
-   **`server.py`**: The core FastAPI application that exposes API endpoints for the dashboard. It uses `build_app` to configure roots for run discovery and optionally a default run. It serves a static Single Page Application (SPA) frontend and handles requests for run summaries, live state, program details, LaTeX equations (via POST for generation), generated feedback/fit images, and newly added **optimization trajectory images** (`/api/runs/{run_id}/trajectory_image/{idx}`). It resolves `run_id` to on-disk directories from configured `run_roots` using `_resolve`.
-   **`static/`**: Contains the HTML, JavaScript (Alpine.js-driven `app.js` for UI logic, Plotly.js for charting, KaTeX for LaTeX rendering, Highlight.js for code syntax highlighting, Marked for Markdown parsing), and CSS assets for the interactive frontend. The UI now includes a `banned` count in the program statistics and a dedicated "Optimization" tab for displaying trajectory images alongside existing `code`, `latex`, `prompt`, `specs`, `lineage`, and `fit` tabs. ### `edgar/evolution/`
This module encapsulates the core logic of the evolutionary algorithm, managing the programs and their dynamics across "islands."
-   **`__init__.py`**: An empty package initializer.
-   **`program.py`**: Defines the `Program` dataclass, the fundamental unit of evolution. Each `Program` includes:
    *   `BirthCertificate`: Metadata about its origin (generation, island, batch index, parentage, mode, temperature, LLM name). Now also includes `ideas` (a list of ideas injected into the prompt).
    *   `Code`: Stores the Python source code for the numpy `model`, the `parameter_estimator` (now a list of strings to support multiple estimators), the JAX-translated model (`model_jax`), and the `best_param_est` (the `param_est` that yielded the lowest loss).
    *   `name`: A descriptive name provided by the LLM.
    *   `program_losses`: Stores initial and final scalar losses for `discover` and `validate` splits, including a complexity penalty. `NotValidated` is a sentinel class marking programs not yet prepared for validation scoring. `LossStats` (formerly `LossPair`) and `Losses` dataclasses structure these, with `LossStats` now including `trajectories` (optimization histories).
    *   `sample_losses`, `sample_losses_init`: Per-sample loss values (no penalty) for final and initial parameters respectively, used for analysis.
    *   `n_params`: The count of free parameters in the model.
    *   `eval_fingerprint`: A low-dimensional representation of model outputs used for deduplication.
    *   `params`, `params_init`: The optimized and initial parameter sets, respectively (as JAX pytrees).
    *   `image_path`, `fit_image_path`, `trajectory_image_path`: Paths to associated visualization images.
    *   `idx`: A global unique identifier within the `Population`, set automatically upon addition.
    *   `rank`: Its final rank based on validation loss.
    *   `best_estimator_idx`: The index of the parameter estimator (from `code.param_est`) that yielded the best score.
    *   `_default_params`: Internal storage for default parameters, with a setter that automatically calculates and caches `n_params` and handles errors gracefully, warning instead of failing.
    *   `compile_model`: Method to dynamically load the JAX model.
    *   `compile_param_ests`: Method to dynamically load all `parameter_estimator` callables from their source strings, now returning a list of callables and handling individual compilation failures gracefully.
    *   Properties (`descriptive_name`, `loss_discover`, `model_code`, `param_est_code`, `default_params`) provide a standardized interface for prompt templating. `param_est_code` now specifically returns `best_param_est`.
-   **`population.py`**: Manages the collection of all `Program` instances throughout an experiment. It is an append-only list, automatically assigning a stable global index (`program.idx`) upon addition. This class handles the persistence of all program data (including numpy arrays for fingerprints and parameters, converted via `_params_to_json` and `_params_from_json`) to a JSONL file (`population.jsonl`) via atomic writes, ensuring data integrity during live runs. It also provides methods for `prepare_validation_scoring` (setting a program's validation loss to `None` for scoring eligibility) and retrieving a rank-sorted copy (`get_sorted`). The loading mechanism (`Population.load`) now correctly handles the new `LossStats` structure including `trajectories` and the `trajectory_image_path`.
-   **`island.py`**: Implements the "island" model of evolutionary computation, where `n_islands` distinct populations evolve somewhat independently but exchange programs.
    *   `seed`: Initializes the `Population` with user-provided seed programs and distributes their indices across all islands.
    *   `spawn`: Selects parents (using `uniform_sample` or `boltzmann_sample`), creates new `Program` shells with `BirthCertificate` metadata, and adds them to their respective islands. `boltzmann_sample` uses a Boltzmann distribution over relative, std-normalized losses to bias selection towards better-performing programs, with a `temperature` parameter controlling the selection pressure. `_safe_loss` (from `scoring.utils`) is now used for robust loss handling in `boltzmann_sample`.
    *   `prune`: Reduces the size of each island by retaining `critical_population_size - n_migrants` best programs, explicitly handling `None`/`inf` losses and ensuring that only `alive` programs are marked `pruned`.
    *   `uniform_sample`: Selects `k` program indices uniformly at random.
    *   `boltzmann_sample`: Selects `k` program indices using a Boltzmann distribution over relative, std-normalized losses. It robustly handles `NaN`/`inf` losses by converting them to `float("inf")` and then to `worst_finite + 1.0` before computing probabilities, ensuring robust sampling. It now uses `_safe_loss` for loss calculations.
    *   `migrate`: Facilitates genetic exchange between islands. Programs are sampled via a Boltzmann distribution (with a warped temperature `T_warped = (T - 1.0) ** 4` for stronger selection later in the run) and moved to destination islands as defined by a `topology` configuration.
    *   `_are_duplicates`: Helper function to determine if two programs are functionally identical based on parameter count, loss similarity (within `loss_tol`), and high cosine similarity of `eval_fingerprint` arrays.
    *   `deduplicate_inner`: Removes functionally identical programs within an island, keeping the lower-loss version.
    *   `deduplicate_outer`: Identifies and removes duplicate programs across different islands, prioritizing the lower-loss (or lower-indexed island's) version. It explicitly handles cases where the same program index might appear on different islands due to migration, ensuring it's kept only on the lower-indexed island. It assumes `deduplicate_inner` has already been run and only applies if islands exceed `min_island_size`.
    *   `deduplicate`: Orchestrates both inner and outer deduplication, using configurable `loss_tol`, `cosine_tol`, and `min_island_size` (derived from `0.75 * critical_population_size`).
    *   `save_island_census`, `load_island_census`: Manages the persistence of island membership history (generation snapshots `census[generation][island_idx] -> list[int]`) to `island_census.jsonl` using atomic writes.

This file is crucial for the dashboard's live monitoring capabilities. -   **`task_spec.py`**: Defines the `TaskSpec` dataclass, a frozen, comprehensive bundle of all configuration and callable functions required to execute or reproduce an EDGAR experiment.
    *   It captures `git_sha` and `git_dirty` status at creation via `_git_state` for full reproducibility. The git commands now explicitly use `REPO_ROOT` for context.
    *   It loads project-specific callables (`load_data_fn`, `loss_fn`, `plot_fn`) and seed `Program` objects directly from source code via `load_function_from_source`, facilitating dynamic code loading. `loss_fn` can now be a single callable or a tuple `(loss_fn_train, loss_fn_test)` for separate training and testing loss calculations, handled by the new `_load_loss_fn` helper. It extracts `DEFAULT_PARAMS` from seed models using `_extract_default_params`.
    *   `from_config` factory method initializes the `TaskSpec` from a `Config` object, setting up the `rng` with a `random_seed` and loading seed programs.
    *   `save` method writes a read-only `task_spec.yaml` to the run directory, preserving the exact configuration and source references. Write permissions are stripped (`os.chmod(path, stat.S_IREAD)`) to prevent accidental modification.
    *   `schedule` determines the `mode` (explore/exploit), `temperature` (decaying from 2 to ~1.37 on a Gemini-scale), and specific LLM models to use for each generation, potentially cycling through lists of LLMs. The transition point from "explore" to "exploit" is now controlled by the `exploit_point` configuration parameter. It handles Anthropic-specific rescaling of temperatures in `llm_calling.py`.
    *   `output_dir` defines the hierarchical run output path as `<save_path>/<task_name>/YYYY-MM-DD/HH-MM-SS/`.
    *   `flat_config` provides a merged dictionary of configuration parameters for convenient lookup by prompt templating.
    *   `prompt_schemas` provides namedtuple access to `model_prompt_schema`, `param_est_prompt_schema`, and `jax_model_prompt_schema`.

### `edgar/run.py`
This is the main orchestrator for an EDGAR experiment. The `run` asynchronous function executes the entire evolutionary loop:
-   **Initialization**: Sets JAX/XLA environment variables (`XLA_PYTHON_CLIENT_PREALLOCATE`, `XLA_PYTHON_CLIENT_ALLOCATOR`, `XLA_FLAGS`) for GPU memory management. It creates the output directory, saves the `TaskSpec`, and initializes structured logging (`run.log`) and status tracking (`status.json`). It loads data from `spec.load_data_fn` into `X_discover`, `X_validate`, `X_eval` splits. `RetryConfig` for LLM calls is also initialized.
-   **Seed Phase**: Initializes the `Population` with provided seed programs, translates their numpy models to JAX, scores them on the `discover` split, generates initial program fit and trajectory visualizations (`generate_program_images`), and saves the initial `Population` and `Island` census. The `status.json` is updated to 'running'.
-   **Generational Loop**: For each generation:
    1.  Logs generation details, including `mode` (explore/exploit), `temperature`, and the selected LLM models from `spec.schedule`.
    2.  `spawn` new programs on islands, generating empty program shells based on parent programs selected via Boltzmann or uniform sampling using `spec.rng`.
    3.  Asynchronously calls LLMs (via `edgar/llm/generate.py`) to fill in `model` code (`generate_models`), `parameter_estimator` code (`generate_param_ests`), and JAX translations (`translate_programs`) for the newly spawned programs. Image feedback for LLMs is generated here.
    4.  `score` the newly generated programs on the discover split, performing parameter estimation and gradient descent. This phase also generates program fit and trajectory images.
    5.  Applies evolutionary operations: `deduplicate` programs within and across islands, `prune` islands to maintain size limits, and `migrate` programs between islands.
    6.  Logs the current generation's summary and persists the `Population` and island `census` (using atomic writes for robustness) and updates the `status.json`.
-   **Final Validation**: After the generational loop, programs are prepared for final `validate` scoring via `population.prepare_validation_scoring`, then `rank`ed based on their validation performance.
-   **Error Handling**: A `finally` block ensures that the `Population`, `census`, and `status.json` are always saved, even if an exception occurs. It captures and logs any encountered errors, marking the run status as 'failed' if an exception was raised, and includes the full traceback.

### `edgar/scoring/`
This module is responsible for evaluating the performance of generated models. It utilizes JAX for efficient numerical operations and runs scoring in subprocesses to ensure stability and enforce timeouts.
-   **`__init__.py`**: An empty package initializer.
-   **`optimizer.py`**: **New module.** Provides the `Optimizer` class for efficient JAX-based gradient descent. This class is designed to be JIT-compiled and uses `jax.lax.scan` to execute the optimization loop entirely on-device, supporting parallel optimization of multiple initial parameter sets.
    *   `flatten_and_init_params`: Flattens initial parameter PyTrees and initializes Optax state.
    *   `_scalar_loss_single`, `_loss_and_grad_batched`: Compute batched losses and gradients for parallel optimizations.
    *   `_step_fn`: The core step function for `jax.lax.scan`, performing a single gradient descent update and tracking best losses/parameters.
    *   `run_optimization`: The JIT-compiled main entry point for running the optimization loop, returning optimized parameters and loss trajectories.
-   **`scoring.py`**:
    *   `_get_params`: Uses the `param_est_fn` from a program to estimate initial parameters per sample. If the estimator fails or is absent, it falls back to the model's `default_params` (stacked for batch processing).
    *   `_optimize`: Orchestrates gradient descent. It now takes a list of initial parameter sets and uses the `Optimizer` class (from `edgar/scoring/optimizer.py`) to perform parallel gradient descent for `n_param_ests` independent optimizations. It returns a list of optimized parameter sets and their corresponding loss trajectories.
    *   `_eval_loss`: Computes the overall scalar loss (including a parameter complexity penalty from `param_penalty_weight`) for a model on a test dataset, using `_evaluate_scalar_loss` from `utils.py`.
    *   `_eval_sample_losses`: Computes individual losses for each sample, without the complexity penalty, using `_evaluate_sample_losses` from `utils.py`.
    *   `_eval_fingerprint`: Generates a low-dimensional "fingerprint" of model outputs on a small subset of data, crucial for `deduplication`, using `_evaluate_model_output` from `utils.py`.
    *   `_worker`: A function executed in a dedicated subprocess. It deserializes a `Program` and `loss_fn` (which can now be `loss_fn_train` or `loss_fn_test` from a tuple) using `cloudpickle`, compiles its JAX model and **all** `parameter_estimator` functions. It then runs multiple parallel optimizations (`n_param_ests`), selects the best-performing one, and computes final losses, fingerprints, and sample-specific losses. This isolation prevents runaway models from crashing the main process and allows for `timeout_s` enforcement. It now returns the `best_idx` and `trajectories` alongside other results.
    *   **New**: `_is_banned`: Helper function to check if a program's JAX model code contains any configured `banned_strings`, marking the program as "banned" if found.
    *   `_score_one_model`: Orchestrates the execution of `_worker` in a separate process (defaulting to "spawn" for compatibility, configurable via `EDGAR_MP_START_METHOD`). It enforces a `timeout_s`; if the subprocess exceeds the timeout, it is forcefully killed, and the program is assigned an infinite loss. It also handles cases where a program has `n_params=None` or contains `banned_strings` by assigning infinite loss and a specific `outcome` label ("inf" or "banned"). It returns a 10-tuple including the outcome, best estimator index, and trajectories.
    *   `_has_jax_code`, `_needs_scoring`: Filters identify programs that have ready JAX models and parameter estimators and whose specific split's `final` loss has not yet been set (or is not already `inf` or `NotValidated`).
    *   `score`: The main scoring function iterates through programs needing evaluation for a given split (`discover` or `validate`). It calls `_score_one_model` for each, then updates the program's `program_losses` (including `trajectories`), `eval_fingerprint`, `params`, `params_init`, `sample_losses`, `sample_losses_init`, and sets `program.best_estimator_idx` and `program.code.best_param_est`. `X_eval` can be passed as `None` to skip fingerprint calculation (e.g., during validation). Scoring metrics (`counters`) now include a "banned" outcome.
    *   `rank`: After all validation scoring is complete, this function assigns a numerical rank to programs based on their `validate.final` loss (excluding `NotValidated` programs), providing a clear measure of final performance. It now uses `_safe_loss` for robust sorting.
-   **`utils.py`**: **New module.** Contains small, reusable JAX-related utility functions:
    *   `_safe_loss`: A robust helper function that maps `None`, `NaN`, and non-finite loss values to `float("inf")` for consistent handling in sorting and comparisons.
    *   `_evaluate_model_output`: Evaluates the model function across batched data and parameters.
    *   `_evaluate_sample_losses`: Computes per-sample losses from model output and data.
    *   `_evaluate_scalar_loss`: Computes the mean scalar loss across all samples.

## Mathematical and Algorithmic Highlights

-   **Evolutionary Algorithm Core**: The system implements an island-model EA. Programs are represented as Python code, forming the genotype. LLMs act as mutation/crossover operators, generating new genotypes.
-   **Boltzmann Sampling**: Used for parent selection and migration, where the probability $P_i$ of selecting a program $i$ is proportional to $e^{g_i}$, with $g_i = -z_i / \max(T_{sampling}, 10^{-3})$ and $z_i = (loss_i - loss_{min}) / (std_{loss} + 10^{-6})$. This ensures that fitter programs (lower loss) have a higher chance of being selected, while the `temperature` parameter controls the exploration/exploitation trade-off. Programs with `None`, `NaN`, or `inf` losses are handled gracefully by mapping them to `float("inf")` via `_safe_loss` before probability calculation.
-   **Parallel Gradient Descent Optimization**: Parameters for evolved models are optimized using `optax.adam` within JAX. The new `edgar/scoring/optimizer.py` module facilitates highly efficient, differentiable fitting of model predictions to data. It supports running `n_param_ests` parallel optimizations for each program (each from a different initial parameter set) using `jax.lax.scan` for on-device execution. JAX's `vmap` and `jit` are extensively used to vectorize and compile these computations across samples and parallel optimizations, and `ravel_pytree` linearizes parameters for optimization.
-   **Deduplication Metrics**: Program similarity for deduplication is assessed via a multi-criterion approach:
    1.  Matching number of parameters (`n_params`).
    2.  Loss difference within a `loss_tol` threshold (e.g., 0.01).
    3.  Cosine similarity of `eval_fingerprint` (model outputs on a small, fixed dataset) exceeding a `cosine_tol` threshold (e.g., 0.95). This robustly identifies functionally identical or near-identical models across `deduplicate_inner` and `deduplicate_outer` operations. `min_island_size` (derived from `0.75 * critical_population_size`) dictates when cross-island deduplication is applied. `deduplicate_outer` now also explicitly handles programs that may appear on multiple islands due to migration.
-   **Temperature and Mode Schedule**: The system dynamically adjusts the temperature for LLM generation and Boltzmann sampling. The base temperature decays from higher values (more exploration, `T=2` at generation 0) to lower values (more exploitation, `T~1.37` at `n_generations`) following `1 + exp(-generation / n_generations)`. A specific `T_warped = (T - 1.0) ** 4` transformation is applied for migration, making migration highly selective in later generations. The `mode` (explore/exploit) transition is now controlled by the `exploit_point` parameter (a fraction of total generations, defaulting to 0.5), allowing for fine-grained control over the evolutionary strategy. This temperature is then rescaled for different LLM providers (e.g., Anthropic's [0,1] range) in `llm_calling.py` to match their API specifications while preserving the relative decay.
-   **JAX Integration**: Critical for performance, JAX is extensively used for model compilation, parameter optimization, and loss calculation, enabling Just-In-Time (JIT) compilation and vectorized operations (`vmap`). This ensures that the generated models can be efficiently evaluated on large datasets and across multiple samples. JAX/XLA environment variables are set early in `run.py` to optimize GPU resource allocation. The new `edgar/llm/utils.py` module provides a helper for translating numpy code to JAX.
-   **Atomic File Operations**: `edgar/io/status.py`, `edgar/evolution/population.py`, and `edgar/evolution/island.py` utilize atomic write operations (write to temp file, then rename using `_tmp_path` for concurrency safety across processes and threads) to guarantee data integrity for files that are frequently updated and polled by external processes (like the dashboard), preventing partial or corrupted data reads. `edgar/io/task_spec.py` further enforces read-only permissions on saved `task_spec.yaml` files to prevent accidental modification and preserve reproducibility.
-   **Subprocess Isolation**: Scoring of individual programs is performed in dedicated subprocesses, allowing for robust timeout enforcement and preventing unstable or resource-intensive models from crashing the main EDGAR process. This also ensures clean JAX environment initialization for each scoring task. `cloudpickle` is used for cross-process object serialization. The subprocess start method is configurable via the `EDGAR_MP_START_METHOD` environment variable (defaults to "spawn"). The `edgar/scoring/scoring.py` module now also implements checks for `banned_strings` in the JAX-translated model code, assigning infinite loss and a "banned" status if such strings are detected.
